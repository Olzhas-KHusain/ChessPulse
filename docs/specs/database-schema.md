# Database Schema (MVP)

Status: implemented in migrations `0001` (Issue 2) and `0003` (engine analysis).
Source of truth for column types and constraints: `backend/app/models/` and
`backend/migrations/versions/`. This document explains the decisions behind them and
records where they differ from `spec.md` §11.

## Overview

```
players ─┬─< games.white_player_id   (RESTRICT)
         ├─< games.black_player_id   (RESTRICT)
         ├─< player_games.player_id  (CASCADE) >─ games.id (CASCADE)
         └─< cache_metadata.player_id (CASCADE, nullable)
openings ──< games.opening_id        (SET NULL, nullable)
games ─┬─< analysis_jobs.game_id     (CASCADE)
       └─< game_analysis.game_id     (CASCADE)
```

| Table            | Purpose                                                                 |
| ---------------- | ----------------------------------------------------------------------- |
| `players`        | Provider accounts: searched players and opponents seen in games         |
| `games`          | One row per provider game, deduplicated across overlapping archives     |
| `player_games`   | A game as part of a **tracked** player's dataset, with color and result |
| `openings`       | Openings identified by a source identifier                              |
| `cache_metadata` | Fetch attempts, last success, expiry and last error per provider resource |
| `analysis_jobs`  | Durable queue of engine-analysis requests, one per `(game, profile)`     |
| `game_analysis`  | Completed engine payload as versioned JSONB, cached per `(game, profile)` |

All primary keys are `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Enumerations are
`VARCHAR` + a named `CHECK` constraint rather than native PostgreSQL `ENUM` types, so
adding a value is an ordinary transactional migration.

## Provider identity (verified 2026-10-20)

Checked against the Chess.com Published-Data API documentation
(<https://www.chess.com/news/view/published-data-api>):

- **Players.** The profile endpoint returns `player_id`, documented as never changing
  for an account, with the caveat that its future availability is not guaranteed and
  that username changes are possible but described as extremely rare. Game records in
  monthly archives identify players only by `username` and `@id` (a URL containing the
  username); `player_id` is not present there.
- **Games.** No dedicated game identifier is documented. Each game has a `url`
  ("URL of this game"); a member `uuid` appears only in a different archive format.

Resulting rules:

| Rule | Decision |
| ---- | -------- |
| Player key | `UNIQUE (provider, username)`, username stored lowercase (`CHECK username = lower(username)`). Chess.com usernames are case-insensitive. |
| Stable player id | `provider_player_id` = profile `player_id`, nullable (opponents known only from game records have none), `UNIQUE (provider, provider_player_id)` when present. |
| Game key | `UNIQUE (provider, provider_game_id)`, `provider_game_id NOT NULL`. |
| Game identifier strategy | Opaque string chosen by the provider adapter (Issue for the Chess.com provider). **Recommendation:** derive it from the game URL as `<namespace>:<numeric id>` (for example `live:123456789`), not from the full URL, so host or path format changes do not create duplicates. |
| No stable identifier | The game is **not persisted**; ingestion records an exclusion reason (`missing_game_identifier`). URLs or usernames are never assumed to be permanent keys. |
| Renamed player | Not resolved silently. Upserting a profile whose `player_id` already belongs to another username raises `IntegrityError`; the provider layer must decide how to merge. Until then, an opponent who renames appears as two opponent rows (rare per provider documentation). |

## Deletion behavior

| Foreign key | On delete | Reason |
| ----------- | --------- | ------ |
| `games.white_player_id`, `games.black_player_id` → `players` | `RESTRICT` | Deleting a participant would make other players' games contradictory; removal must be an explicit cleanup. |
| `player_games.player_id` → `players` | `CASCADE` | A dataset association has no meaning without its player. |
| `player_games.game_id` → `games` | `CASCADE` | Retention cleanup of games removes their associations. |
| `games.opening_id` → `openings` | `SET NULL` | Losing opening metadata must not delete games; they fall into the "Unknown" group. |
| `cache_metadata.player_id` → `players` | `CASCADE` | Freshness metadata of a removed player is meaningless. |
| `analysis_jobs.game_id` → `games` | `CASCADE` | A job for a removed game has nothing to analyse. |
| `game_analysis.game_id` → `games` | `CASCADE` | The payload describes that game only. |

## Consistency rules

- `games`: `white_player_id <> black_player_id`; ratings are `NULL` or `>= 0`.
- `player_games`: `UNIQUE (player_id, game_id)` (no duplicate association) and
  `UNIQUE (game_id, color)` (at most one tracked perspective per side).
- `player_games.color` must match the player's side in `games`, and
  `player_games.result` must equal the game result seen from that side
  (`white_win` + white → `win`, + black → `loss`; `draw` → `draw`; `unknown` → `unknown`).
  This is enforced by two **deferred constraint triggers** (checked at `COMMIT`,
  raising `check_violation` with constraint names `ck_player_games_participant` and
  `ck_player_games_result_matches_game`). Deferral lets a correction update a game and
  its associations in any order within one transaction. The same mapping exists in
  Python as `app.models.player_result_for`, used by the repository.
- `cache_metadata`: `succeeded` requires `last_success_at`; `failed` requires
  `last_error_code` and `last_error_at`; `expires_at` and `record_count` exist only
  after a successful fetch (so a failure can never look like a confirmed empty result);
  `last_error_code` must match `^[A-Z][A-Z0-9_]*$`, which rules out raw error payloads.
- `analysis_jobs`: `UNIQUE (game_id, profile_hash)` (one job per game and profile);
  `attempts >= 0`; `profile_hash` is a 64-character lowercase SHA-256; a `failed` job
  always names an `error_code`; `finished_at` exists only for terminal states.
- `game_analysis`: `UNIQUE (game_id, profile_hash)` (one cached result per profile);
  `depth > 0`; `analysis_ms >= 0`. The payload is versioned JSONB (`schema_version`), so
  a future shape change can be detected instead of silently misread.

## Timestamps

- Every timestamp column is `TIMESTAMP WITH TIME ZONE`.
- The `UtcDateTime` column type rejects naive datetimes on write, converts aware values
  to UTC, and always returns UTC on read, independent of the session `TimeZone`.
- `created_at` / `updated_at` default to the database clock. Repository upserts only
  rewrite a row, and only move `updated_at`, when a value actually changes.
- `games.played_at` is the authoritative timestamp for the analysis window. For
  Chess.com it is the game's `end_time`, the completion time of the game.

## Indexes and query patterns

| Query | Index |
| ----- | ----- |
| Player by normalized username | `uq_players_provider_username (provider, username)` |
| Games of a tracked player | `uq_player_games_player_id_game_id (player_id, game_id)` + `pk_games` |
| Rapid games in a time window | `ix_games_time_class_played_at (time_class, played_at)` |
| Retention cleanup by date | `ix_games_played_at` |
| Games of a participant / FK checks | `ix_games_white_player_id`, `ix_games_black_player_id` |
| Associations of a game (cascade, triggers) | `uq_player_games_game_id_color (game_id, color)` |
| Opening joins / `SET NULL` | `ix_games_opening_id`, `ix_openings_eco_code` |
| Cache maintenance | `ix_cache_metadata_expires_at`, `ix_cache_metadata_player_id` |
| Deduplication | `uq_games_provider_provider_game_id`, `uq_openings_source_source_opening_id`, `uq_cache_metadata_cache_key` |
| Claiming the next analysis job | `ix_analysis_jobs_status_created_at (status, created_at)` + `FOR UPDATE SKIP LOCKED` |
| Reading a cached analysis | `uq_game_analysis_game_profile (game_id, profile_hash)` |
| Invalidating results by profile | `ix_game_analysis_profile_hash` |

`GameRepository.list_player_games` reads a window as **start inclusive, end exclusive**
(spec §6.1), orders by `played_at DESC, games.id DESC` (deterministic tie-breaker), uses
keyset pagination on that pair, caps page size at 200, and loads participants and
opening in the same query. Relationships are declared `lazy="raise"` so accidental
per-row loading fails in tests instead of causing N+1 queries. A denormalized
`(player_id, played_at)` index was not added: MVP windows are small, and it should be
introduced only after measuring.

## Differences from spec.md §11

`spec.md` §11 came in two inconsistent versions; per the product decision, the most
coherent structure was chosen. Differences:

| Spec | Implemented | Reason |
| ---- | ----------- | ------ |
| `games.white_player_id` / `black_player_id` nullable | `NOT NULL` | Every valid game has two participants; a record without them is excluded at ingestion, not stored half-empty. |
| `games.result_white` | `games.result` ∈ `white_win`, `black_win`, `draw`, `unknown` | Unambiguous without a perspective. |
| `games.opening_name` | removed | Duplicates `openings.name`; unresolved openings stay `NULL` and are grouped as "Unknown". |
| `games.source_updated_at` | removed | Chess.com does not provide a per-game update time. |
| — | `games.time_control` added | Needed by game details (spec §6.9); stored raw, never used to infer the time class. |
| `player_games.rating_before` / `rating_after` | removed | The game record supplies one rating per side, stored in `games.white_rating` / `black_rating`. The provider does not document a pre-game rating, and deriving one would fabricate data. Rating history reads these columns through `player_games.color`. |
| `player_games.player_color` / `player_result` (v2 naming) | `color` / `result` | v1 naming, shorter. |
| — | `players.current_rapid_rating`, `current_rapid_rating_at` added | Required by `GET /players/{username}` and the overview; distinct from per-game ratings. |
| `openings.source`, `source_opening_id` nullable | `NOT NULL` | An opening row exists only when a source identifier exists; no placeholder rows. |
| `cache_metadata.status` = fresh / stale / refreshing / unavailable | `refreshing` / `succeeded` / `failed` | Fresh vs stale changes with the clock, so it is derived at read time from `expires_at` instead of stored. |
| `cache_metadata.fetched_at` (v2) | `last_success_at` (v1) | Clearer name. |
| `cache_metadata.last_attempt_at` nullable | `NOT NULL` | A row is created by the first attempt. |
| `player_statistics` | not created | Optional per the issue. A rolling 30-day window changes every request, so per-window caching rarely hits, and invalidation rules are not specified yet. Aggregates are computed from `player_games` + `games`. |

## Migration workflow

Run from `backend/` with the virtual environment active:

```bash
alembic upgrade head                                   # apply
alembic check                                          # fails if models and migrations differ
alembic revision --autogenerate -m "describe change"   # draft a new migration, then review it
alembic downgrade -1                                   # roll back one revision
```

Autogenerate does not detect triggers or functions, and it renders each non-native
enum `CHECK` constraint twice; always review and edit the generated file (see the
header of `0001`). `tests/db/test_migrations.py` verifies that migrations apply to an
empty database, downgrade cleanly, and match the models.
